# GitOps and add-ons

> Explanation · [Documentation](../../README.md#documentation)

How a cluster with an `argocd` section is driven from a Git repository, and
why the add-ons live there too. To set it up: [Set up GitOps](../how-to/set-up-gitops.md),
[Manage the add-ons in Git](../how-to/manage-addons-in-git.md),
[Keep Secrets in Git](../how-to/keep-secrets-in-git.md).

## Argo CD from the first minute

With an `argocd` section the cluster syncs its repository as soon as it
exists. `create` (and later `argocd`):

1. **Checks the repository from the host** with the configured credentials
   (`git ls-remote`, your own git config and credential helpers disabled), so
   a wrong key fails before any VM is built.
2. **Installs Argo CD** with Helm in namespace `argocd`, Dex disabled. For
   SSH repositories the server's host keys go into Argo CD's known hosts;
   when they change, the repo server is restarted, since Kubernetes would
   otherwise take a minute or more to update the file in the running pod.
3. **Creates the repository Secret** `argocd/gitops-repository` with server-side
   apply, so the credentials aren't copied into a
   `last-applied-configuration` annotation.
4. **Creates the root Application** for `repository.path` at
   `repository.revision`: automated sync, `CreateNamespace=true`, retries.
5. **Waits until it is Synced and Healthy,** after a hard refresh, accepting
   only a status computed after it: success reflects the current credentials.
   A persistent error fails after about two minutes with Argo CD's message;
   slow workloads get up to 10 minutes.

Argo CD polls every 3 minutes, so a push lands within 3–4 minutes unless the
Git server calls a webhook.

## Add-ons in Git

Without `addons.enabled`, the add-ons (Cilium, Argo CD, cert-manager,
Headlamp, Longhorn, the gateway, the issuer, certificates, routes) are Helm
releases the script installs. With it, they are Argo CD Applications in the
repository ([files](../reference/repository-files.md)), and the script's job
becomes rendering them and pushing them.

**Why.** The repository then holds the cluster's whole Argo CD view, its own
root included: a rebuilt Argo CD finds everything again, every change is a
commit, and a merge check can see add-ons and applications alike.

**The app-of-apps.** The Application `addons` syncs `addons/` recursively: the
generated Applications in `addons/generated/` and any written by hand in
`addons/` itself. Each *topic* (`generated/<topic>/`: the manifests and
Secrets of one concern) is synced by the add-on of the same name as a second
source, or by its own Application when there is no chart (`ingress`,
`talos-backup`).

**Taking over Helm releases.** Each Application keeps the release name the
script used with Helm, so Argo CD adopts the existing resources instead of
creating new ones. Once an add-on is Synced, Helm's record of the release is
deleted (the resources stay), so `helm upgrade` or `helm uninstall` can no
longer fight Argo CD.

**What can't be in Git.**
- The repository credential: Argo CD needs it to read the repository.
- The node layout: the LoadBalancer pool and the ARP policy change with
  `scale` and `longhorn`.
- The bootstrap: Cilium (no network without it) and Argo CD are first
  installed with Helm by `create`; Argo CD adopts them in the same run.

**Projects.** The generated add-ons are in an "infra" project, except
those that need nothing cluster-wide but their namespace (`headlamp`,
`ingress`, `talos-backup`), in a "services" project: by default
`platform-infra` and `platform-services` (`argocd.addons.projects`). The two roots stay in
`default`: the projects are AppProjects in the repository that the
app-of-apps creates, so it can't wait for one.

## Who is the source: `generate` or `reuse`

- **`generate`** (default): the cluster file is the source. Each run renders
  and pushes again; edits made in the repository are overwritten, files no
  longer generated are removed. `generated/CHECKSUMS` lets the repository
  refuse edits by hand.
- **`reuse`**: Git is the source. Files already in the repository are kept,
  edits included, nothing is removed; only missing files are written (a new
  add-on, a new cluster folder). The roots are applied from their files in
  Git.

Files without the `Generated by deploy-talos.py` header are never touched,
which is what lets hand-written Applications live next to the generated ones.

## Safety

- **Pruning:** Cilium and Argo CD never prune, so a resource dropped from the
  chart can't take down the network or Argo CD itself. The other add-ons
  prune.
- **Self-heal:** every Application reverts manual changes in the cluster.
- **Deterministic rendering:** a chart that generates keys renders
  differently on every refresh and Argo CD would keep applying it. Cilium's
  Hubble certificates are therefore made by a job in the cluster
  (`hubble.tls.auto.method: cronJob`).
- **Hooks:** Longhorn's pre-upgrade job (a Helm hook Argo CD would run before
  every sync) is off, as Longhorn recommends for Argo CD.
- **No cascade:** the generated Applications carry no deletion finalizer.
  Removing a section deletes its Application, not what it deployed.

## Secrets in Git

With `addons.sopsAgeKeyFile`, the add-on Secrets live in the repository too,
encrypted with [SOPS](https://getsops.io) for age keys and decrypted by Argo CD
with [KSOPS](https://github.com/viaduct-ai/kustomize-sops).

- **Readable structure.** Only `data`/`stringData` values are encrypted:
  names and keys stay readable, so a diff shows which key changed.
- **What stays out:** the repository credential and the cluster's age key
  (Secret `argocd/sops-age`, mounted into the repo server). Both are needed
  before anything in Git can be read.
- **Trust.** The repo server gets the `ksops` binary (init container
  `viaductoss/ksops`) and `kustomize.buildOptions: --enable-alpha-plugins
  --enable-exec`: it runs plugins named in the repository. That is
  acceptable for your own repository and a wider grant than plain manifests.
- **Git wins for what it holds.** A credential already in the repository is
  used, never replaced: the client secrets in Git are set on their Keycloak
  clients, so a rebuilt Keycloak gets the same secrets back; the talos-backup
  S3 keys in Git are kept even if the files differ (with a warning).
- **No churn.** SOPS encryption isn't deterministic, so the script decrypts
  what is in the repository and only rewrites a file when its content or its
  recipients changed.
- **Rebuilds.** A rebuilt cluster gets the same age key from its file, so
  everything in Git decrypts again. Losing every key that can decrypt means
  re-creating the Secrets: keep yours (`addons.sopsRecipients`) off the host.

## Repository layouts

The root Application applies whatever is in `repository.path`:

- **Plain manifests,** with `recurse: true` for subdirectories.
- **App of apps:** `Application` manifests (namespace `argocd`) pointing at
  other paths or repositories; new applications are a commit, not a change
  to the cluster.
- **Base and overlays:** `base/<app>/` with the manifests, and per cluster
  `clusters/<name>/<app>/kustomization.yaml` including the base and patching
  what differs, plus that cluster's encrypted Secrets.

## Access and trust

Argo CD only reads the repository, so its credential should only read: a
read-only deploy key, or a token scoped to reading. Pushing the add-ons uses a
separate write credential (`addons.pushSshKeyFile` / `pushTokenFile`) that
stays on the host. More in [Security](security.md#argo-cd-credentials).
